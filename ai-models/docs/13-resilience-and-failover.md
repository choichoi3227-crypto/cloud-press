# 장애 대응 및 이중화 설계

## 1. 무엇을 막으려는 것인가

사용자 요청: "서비스 장애 발생 시, 서비스 완전 불가 사태 방지". 이걸 정직하게 분해하면, 이 아키텍처에는 **서로 독립적으로 장애가 날 수 있는 세 개의 시스템**이 있습니다.

| 시스템 | 장애 시 영향 범위 |
|---|---|
| WordPress (PHP+MySQL) | 로그인, 마이페이지, 일반 페이지 열람 불가 |
| Cloudflare Worker | API 요청 전체(텍스트/이미지 생성) 불가 |
| 추론 서버 (FastAPI) | 실제 모델 응답만 불가 (Worker/WordPress는 살아있음) |

**중요한 사실을 먼저 짚습니다**: 이 세 시스템은 애초에 물리적으로 분리되어 있기 때문에("호스팅 위치가 다름"), 한 곳이 죽어도 나머지는 원칙적으로 살아있을 수 있는 구조입니다. 이게 이 아키텍처가 처음부터 갖고 있던 이점이고, 지금 하려는 건 이 이점을 실제로 살리는 구체적인 장치를 추가하는 것입니다.

다만 "완전한 이중화"(모든 컴포넌트를 다중화해서 하나가 죽어도 100% 무중단)는 비용이 크게 늘어나는 방향이라, 사용자가 원했던 "서버비 절감" 원칙과 충돌합니다. 그래서 여기서는 **비용을 거의 늘리지 않으면서 "완전 불가"만은 막는** 실용적인 수준으로 설계합니다.

## 2. 시나리오별 대응

### 2.1 추론 서버 장애 (가장 자주 발생할 가능성이 높은 지점)

이미 기존 설계에 반영되어 있습니다 (`01-architecture-detail.md` 3절). Worker가 추론 서버 응답을 못 받으면:

- 캐시에 동일 요청이 있으면 캐시로 응답 (완전 실패 아님)
- 캐시도 없으면 503 + "잠시 후 다시 시도" 메시지 반환
- WordPress `cloud-press-connector`는 이 503을 받으면 마이페이지 콘솔에 "지금 모델 서버가 점검 중이에요"라는 **사용자 친화적 메시지**로 변환해서 보여줍니다 (에러 스택트레이스를 그대로 노출하지 않음).
- 이 경우에도 **WordPress 자체(로그인, 마이페이지 열람, 다른 글 읽기)는 100% 정상 작동**합니다 — 추론 서버 장애가 사이트 전체를 끌고 내려가지 않습니다. 이게 계층을 분리해둔 핵심 이유입니다.

추가 안전장치로, 추론 서버를 **무료/저가 티어 두 곳에 동일하게 배포**하고 Worker의 `INFERENCE_SERVER_URL`을 1차/2차로 구성하는 것을 권장합니다 (완전 무료로 가능 — `09-running-without-gpu.md`에서 소개한 Fly.io, Railway 등은 여러 개 무료 인스턴스를 동시에 굴리는 데 추가 고정비가 들지 않습니다).

```typescript
// lib/inferenceClient.ts 확장안
async function callInferenceServerWithFallback(env: Env, path: string, body: unknown) {
  const primary = await callInferenceServer(env, env.INFERENCE_SERVER_URL, path, body);
  if (primary.ok) return primary;

  if (env.INFERENCE_SERVER_URL_BACKUP) {
    return callInferenceServer(env, env.INFERENCE_SERVER_URL_BACKUP, path, body);
  }
  return primary;
}
```

### 2.2 Cloudflare Worker 장애

Cloudflare 자체의 글로벌 장애는 매우 드물지만(SLA가 매우 높은 서비스), 발생하면 API 전체가 영향받습니다. 이 경우:

- WordPress `cloud-press-connector`가 Worker 호출 타임아웃/오류를 감지하면, 마이페이지에 "AI 모델 서비스가 일시적으로 응답하지 않습니다"라고 표시하고 **나머지 WordPress 페이지(로그인, 콘텐츠 열람)는 계속 서비스**합니다.
- 별도의 Worker 이중화(다른 CDN에 동일 게이트웨이 배포)는 비용/복잡도 대비 이득이 크지 않아 권장하지 않습니다 — Cloudflare 자체가 이미 매우 안정적인 인프라이므로, 이 부분까지 이중화하는 것은 실용적 우선순위가 낮습니다.

### 2.3 WordPress 장애 (호스팅사 장애, PHP/MySQL 다운 등)

가장 큰 리스크입니다. WordPress가 죽으면 로그인/마이페이지/일반 페이지가 전부 안 보입니다. 완전 이중화(별도 서버에 실시간 복제)는 비용이 들지만, **비용을 거의 늘리지 않는 최소한의 장치**는 다음과 같습니다.

1. **정적 장애 안내 페이지를 Cloudflare Pages에 별도로 미리 배포**해둡니다 (`frontend/status/`). 이건 WordPress와 완전히 분리된 인프라(Cloudflare, 이미 무료)에 있으므로 WordPress가 죽어도 살아있습니다.
2. Cloudflare에서 해당 도메인의 헬스체크(예: Cloudflare Health Checks 또는 무료 외부 모니터링 서비스)로 WordPress 응답을 주기적으로 확인하고, 장애 감지 시 DNS 또는 Cloudflare의 "Always Online" 유사 기능으로 정적 안내 페이지로 자동 전환하는 것을 검토합니다. (정확한 기능명과 사용 가능 여부는 Cloudflare 플랜에 따라 다르므로, 실제 적용 시 최신 Cloudflare 문서를 확인해야 합니다 — 이 문서 작성 시점 기준으로 확정하지 않습니다.)
3. **핵심 API(Worker+추론서버)는 WordPress와 완전히 독립된 인프라이므로, WordPress가 죽어도 API 자체를 직접 호출하는 것은 계속 가능합니다.** 즉 "서비스 완전 불가"는 막아지고, "웹사이트 UI 접근 불가"만 남습니다 — 이 차이가 이 아키텍처가 애초에 제공하는 안전판입니다.
4. **정기 백업**: WordPress 데이터베이스(회원 정보, 글)는 최소 매일 1회 자동 백업하고, 별도 스토리지(예: Cloudflare R2, 이미 인프라에 있는 서비스라 추가 계약 불필요)에 보관합니다. 대부분의 자체 호스팅사가 기본 백업 도구를 제공하므로, 이미 결제한 호스팅의 백업 기능을 우선 확인하고 부족하면 플러그인(예: 널리 쓰이는 백업 플러그인)으로 보완합니다.

### 2.4 데이터베이스(MySQL) 장애

- 호스팅사의 자동 백업/복구 기능이 있는지 우선 확인 (이미 결제한 상품에 포함되어 있을 가능성이 높습니다)
- `wp-config.php`의 `DB_HOST`를 호스팅사가 제공하는 경우 별도 조치가 필요 없지만, 자체 관리형 MySQL이라면 최소 일 1회 `mysqldump` 자동화를 cron으로 걸어두는 것을 권장합니다.

## 3. 우선순위 정리 (비용 대비 효과)

| 조치 | 비용 | 효과 | 우선순위 |
|---|---|---|---|
| Worker의 추론 서버 응답 실패 시 사용자 친화적 메시지 처리 | 없음 (코드만 추가) | 사용자가 에러를 마주쳐도 서비스가 "죽은 것처럼" 보이지 않음 | 높음 |
| 추론 서버 2중 배포 (무료 티어 두 곳) | 없음 (무료 티어 재사용) | 추론 서버 장애 시에도 API 정상 응답 | 높음 |
| WordPress DB 정기 백업 | 없음~매우 저렴 (대부분 호스팅에 포함) | 최악의 경우에도 데이터 손실 최소화 | 높음 |
| Cloudflare Pages에 정적 장애 안내 페이지 | 없음 (Pages 무료) | WordPress 다운 시에도 사용자에게 상황 안내 가능 | 중간 |
| WordPress 자체를 여러 서버에 이중화 | 있음 (서버 추가 비용) | WordPress 다운타임 자체를 없앰 | 낮음 (요청하신 "서버비 절감" 원칙과 충돌하므로 지금 단계에서는 보류 권장) |

**권장**: 지금 단계에서는 "높음"으로 표시한 3가지(에러 처리, 추론 서버 2중화, DB 백업)만 구현하고, WordPress 자체의 완전 이중화는 트래픽이 실제로 늘어나 그만한 투자가 정당화될 때 재검토하는 것을 제안합니다. 이렇게 하면 추가 고정비 없이 "서비스 완전 불가" 시나리오의 대부분을 방지할 수 있습니다.
