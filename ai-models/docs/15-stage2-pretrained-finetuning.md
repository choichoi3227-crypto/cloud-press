# 단계 2 방향 전환 — 사전학습 베이스 모델 파인튜닝

## 1. 이 문서가 왜 필요한가

`docs/03-flash-texter-spec.md`, `docs/04-nano-tech-artist-spec.md`는 원래 "완전히 처음부터(from scratch) 직접 학습"을 전제로 작성되었습니다. 실제로 단계 1(의도 분류 GRU, 조건부 소형 GAN)은 이 원칙대로 구현되어 검증까지 마쳤습니다.

이후 목표가 명확해졌습니다: **"Gemini 3.5 Flash / Nano Banana 2 방향으로 실제 품질을 끌어올리되, 학습 비용은 100% 무료(Colab/Kaggle), 실제 서비스 추론은 GPU 없이(CPU)"**. 이 세 조건을 모두 만족하면서 처음부터 직접 학습(from scratch)까지 지키는 것은 물리적으로 불가능합니다 — 처음부터 학습해서 Flash급 품질에 도달하려면 최소 수백억 원대의 GPU 클러스터와 수조 토�큰의 데이터가 필요하기 때문입니다 (`docs/00-overview.md`의 최초 전제 참조).

**따라서 원칙을 다음과 같이 명확히 재정의합니다.**

| | 단계 1 (기존, 유지) | 단계 2 (이 문서, 신규) |
|---|---|---|
| 학습 방식 | 처음부터 직접 학습 (from scratch) | **검증된 오픈소스 사전학습 가중치를 베이스로 파인튜닝** |
| 학습 데이터 | 직접 제작한 시드 데이터 | **직접 제작한 데이터 위주** (외부 서비스 의존 최소화, `docs/14`의 검색 API 연동은 추론 시점 보조 자료일 뿐 학습 데이터가 아님) |
| 학습 인프라 | Colab/Kaggle 무료 GPU | 동일 |
| 추론 인프라 | CPU | 동일, 단 모델이 커진 만큼 양자화 필수 |
| **실제 서비스에서의 역할** | **폴백(2차 안전망)** — Qwen3.5 로드 실패, 추론 오류 등 예외 상황에서만 응답 | **주력** — 정상 상황에서는 항상 이 경로로 실제 신경망이 추론해 응답 생성 |

**폴백 전략(사용자 확정 사항)**: 단계 1(의도 분류+응답 검색)을 완전히 폐기하지 않고 유지합니다. 이유는 (1) 이미 완성되어 검증까지 마친 인프라이고, (2) Qwen3.5 로드가 실패하거나(메모리 부족, 파일 손상 등) 추론 중 예외가 발생했을 때 완전히 서비스가 죽는 대신 최소한의 응답을 계속할 수 있는 안전망 역할을 하기 때문입니다. `inference-server/models/flash_texter.py`의 로딩 우선순위는 "Qwen3.5 LoRA 로드 시도 → 실패 시 단계 1 GRU로 폴백 → 그마저 없으면 더미 응답"의 3단계 구조로 설계합니다 (5절 참조).

"직접 학습"의 의미가 "모델 가중치를 처음부터 만든다"에서 "우리 목적에 맞는 데이터로 모델을 실제로 훈련시킨다(파인튜닝도 훈련이다)"로 조정됩니다. 파인튜닝 데이터셋 자체는 여전히 100% 직접 제작합니다 — 이 부분은 바뀌지 않습니다.

## 2. 베이스 모델 선정 (실제 조사 기반, 2026년 9월 기준)

### 2.1 텍스트: Qwen3.5-0.8B

처음 후보로 검토했던 Llama 3.2 1B 대신, 실제 조사 결과 더 적합한 모델을 확정했습니다.

**중요한 정정 (2026-09 재조사)**: 최초 조사 시점에는 Qwen3.5-0.8B를 순수 텍스트 모델로 파악했으나, 이후 더 깊이 조사한 결과 **Qwen3.5는 처음부터 비전-언어(멀티모달) 모델로 설계되었다**는 사실을 확인했습니다 (공식 모델 카드: "0.8B parameter vision-language model", NVIDIA NGC 카탈로그에도 "Vision-Language Model"로 명시). 즉 `AutoModelForCausalLM.from_pretrained("Qwen/Qwen3.5-0.8B-Base")`를 그대로 호출하면 비전 인코더(SigLIP 계열 ViT)와 비전-텍스트 프로젝터까지 함께 로드되어, 우리가 원하는 "가벼운 텍스트 전용 CPU 추론"에 불필요한 파라미터와 메모리를 더하게 됩니다.

**대응 방침**: 두 가지 실행 경로를 함께 준비합니다.
1. **text-only 추출 버전 사용**: 커뮤니티가 이미 비전 인코더를 제거하고 텍스트 백본만 남긴 파생 체크포인트를 공개하는 사례가 확인됩니다 (예: `tuandunghcmut/Qwen3.5-9B-text-only`, 이 저장소가 공개한 방법대로 `Qwen3_5ForCausalLM`/`qwen3_5_text` 아키텍처만 남기고 vision encoder, patch merger, 이미지/비디오 토큰 라우팅, MTP 헤드를 제거). 0.8B 크기의 동일한 text-only 추출본이 있는지 Colab에서 실제로 검색·확인해야 합니다 — 없다면 직접 추출하는 스크립트를 작성해야 할 수 있습니다.
2. **vLLM의 `--language-model-only` 플래그 활용**: 서빙 단계에서는 공식적으로 이 플래그가 비전 프로파일링/인코더를 건너뛰고 메모리를 절약하도록 지원됩니다. 다만 이는 vLLM 서빙 시나리오이고, `transformers`의 `AutoModelForCausalLM`/`peft`로 하는 우리 LoRA 파인튜닝 스크립트에 직접 적용되는 옵션은 아니므로, 파인튜닝 자체보다는 이후 추론 서버에 vLLM을 도입할 경우에 유효한 선택지입니다.

이 문제는 `train_lora.py` 실행 전에 반드시 해결해야 하는 선행 조건이며, 3절 "진행 상황"에 이 재조사와 다음 단계를 기록합니다.

| 항목 | 내용 |
|---|---|
| 저장소 | `Qwen/Qwen3.5-0.8B-Base` (파인튜닝용), `Qwen/Qwen3.5-0.8B` (참고용 instruct 버전) — **둘 다 비전-언어 모델** |
| 파라미터 | 약 0.8B (텍스트 백본만이 아니라 비전 인코더 포함 전체 기준) |
| 라이선스 | Apache 2.0 (상업적 이용/재배포 제약 적음) |
| 언어 지원 | 200개 이상 언어 (한국어 포함, Llama 3.2보다 다국어 강점 큼) |
| 아키텍처 특징 | Gated Delta Networks(선형 어텐션) + 일정 간격의 표준 전체 어텐션이 섞인 하이브리드 텍스트 백본, 그 위에 비전 인코더가 결합된 구조. `transformers >= 5.2.0` 필수 (그 이전 버전은 아예 로드 불가 — 실측 확인) |
| 컨텍스트 길이 | 262,144 토큰 기본, 최대 1,010,000 토큰까지 확장 가능 |
| 응답 모드 | thinking / non-thinking 모드 전환 지원, 기본값은 non-thinking(빠른 응답) |
| 파인튜닝 적합성 | Base 모델에 `<\|im_start\|>` 등 대화 제어 토큰이 이미 학습되어 있어, 임베딩까지 재학습할 필요 없이 LoRA만으로 효율적 파인튜닝 가능 |
| 알려진 이슈 | (a) `dtype` 인자가 무시되고 항상 bfloat16으로 로드되는 버그가 일부 composite 체크포인트에서 보고됨 (transformers issue #46459) — 구체 클래스(`Qwen3_5ForCausalLM`)를 직접 쓰면 우회 가능. (b) `AutoModelForSequenceClassification` 등 일부 Auto 클래스가 아직 `Qwen3_5Config`를 인식하지 못하는 이슈가 있으나, 우리가 쓰는 `AutoModelForCausalLM` 경로는 영향받지 않음. |

**Base vs Instruct 선택**: 파인튜닝 목적이므로 `Qwen3.5-0.8B-Base`(사전학습 전용, 아직 대화 형태로 조정되지 않음)에서 시작해 우리 데이터로 직접 instruct 튜닝을 하는 것이 "직접 학습" 원칙에 더 부합합니다. 다만 Colab 자원이 제한적이라면 이미 instruct 튜닝된 `Qwen3.5-0.8B`에서 우리 도메인에 맞게 추가 파인튜닝(continued fine-tuning)하는 것도 현실적 대안입니다. `03-flash-texter-spec.md` 갱신판(3절)에서 두 경로를 모두 다룹니다.

**thinking/non-thinking 모드**가 사용자가 요구한 "Claude처럼 유동적으로 속도 조절, 짧은 질문엔 빠르게, 긴 설명엔 자세히"와 정확히 대응됩니다 — 이 모드 전환을 추론 서버의 요청 파라미터로 노출합니다 (4절 참조).

### 2.2 이미지: Sana-0.6B

BK-SDM-Small 대신 실제 조사로 확인한 더 나은 후보로 교체합니다.

| 항목 | 내용 |
|---|---|
| 저장소 | `Efficient-Large-Model/Sana_600M_512px_diffusers` (경량), 1024px/1.6B 버전도 존재 |
| 파라미터 | 590M (0.6B) |
| 라이선스 | Apache 2.0 |
| 개발 | NVIDIA + MIT HAN Lab |
| 핵심 기술 | Deep Compression Autoencoder(32배 압축), Linear DiT(선형 어텐션으로 연산량 절감), 4bit 양자화 버전 공식 지원(SVDQuant+Nunchaku) |
| 실측 성능 | Flux-12B(20배 큰 모델)와 경쟁할 품질, 100배+ 빠른 처리량. 16GB급 GPU에서 1024×1024 이미지를 1초 이내 생성 |
| CPU 추론 | 공식 실측 자료는 GPU 기준이며, **CPU 추론 속도는 이 프로젝트에서 직접 실측 필요** (4bit 양자화 적용 시 유의미한 속도 확보 예상, 정확한 수치는 3절 검증 계획 참조) |

Sana는 픽셀 공간이 아니라 극도로 압축된 latent 공간에서 동작하고, attention이 선형 복잡도라서 동급 파라미터 대비 CPU에서도 유리할 가능성이 높지만, **이 문서 작성 시점에는 공식 CPU 벤치마크가 확인되지 않았으므로 과장하지 않습니다.** Colab에서 GPU/CPU 양쪽으로 직접 재보고 실측치를 이 문서에 반영하는 것을 다음 단계로 둡니다.

## 3. 학습 데이터 전략 (외부 의존성 최소화 원칙 유지)

### 3.1 텍스트 파인튜닝 데이터

단계 1의 `generate_seed_data.py`(7개 의도, 280쌍)는 규모가 너무 작아 사전학습된 0.8B 모델의 파인튜닝에는 부족합니다. `generate_finetune_data.py`로 카테고리를 10개로 확장하고 슬롯 기반 템플릿을 도입했습니다.

**실제 생성 결과 (정직하게 기록)**: 템플릿×슬롯 조합을 전량 열거해 중복 없이 생성한 결과, 현재 카테고리/슬롯 규모로는 **913개의 실제로 서로 다른 (입력, 응답) 쌍**이 생성됩니다. 애초 목표였던 "수천 쌍"에는 아직 못 미칩니다. 이전 버전에서는 `repeat_per_template`를 단순히 늘려 3,000행을 만들었지만, 실제로 검사해보니 74%가 중복이었습니다(고유 조합은 775개뿐) — 즉 "쌍의 개수"가 아니라 "중복 없는 실제 조합 수"가 진짜 데이터 규모입니다. 스크립트를 수정해 요청한 개수가 실제 가능한 조합 수를 넘으면 중복을 채우지 않고 가능한 만큼만 생성하도록 고쳤습니다 — 숫자를 부풀리지 않기 위함입니다.

**913개에서 실제 "수천" 규모로 늘리는 방법 (다음 작업)**:
1. **카테고리 추가**: 지금 10개 카테고리 중 `capability`(6개), `identity`(8개), `farewell`(10개)처럼 슬롯이 없는 카테고리는 표현의 최댓값이 낮습니다. 응답 템플릿과 입력 표현을 카테고리당 수십 개로 직접 늘려야 합니다.
2. **슬롯 카테고리 확장이 효율적**: `explain_concept`(현재 300개), `how_to`(300개), `opinion_request`(225개)처럼 슬롯이 있는 카테고리는 슬롯 값 목록만 늘려도 조합이 곱셈으로 늘어납니다. 예: topic 33개 → 66개로 늘리면 explain_concept만 최대 약 1,000개 이상으로 늘어남.
3. **카테고리 자체를 더 추가**: 지금 10개보다 훨씬 많은 실생활 대화 범주(길찾기, 추천, 비교, 요약 요청, 번역 요청 등)를 계속 추가.

이 작업은 반복적이고 품이 드는 작업이라, 다음 세션에서 이어서 카테고리/슬롯을 계속 확장하는 것을 전제로 합니다. **핵심 원칙(외부 서비스 크롤링 없이 전량 직접 작성)은 유지하되, 목표 규모(수천 쌍)에는 아직 도달하지 못한 상태임을 숨기지 않습니다.**

- **검색 API 활용은 학습 데이터 생성이 아니라 추론 시점 보강**(`docs/14`)에 한정 — 학습 데이터 자체는 검색 결과를 크롤링해서 만들지 않습니다. 이는 "외부 의존성 최소화" 원칙을 지키기 위함입니다.

### 3.2 이미지 파인튜닝 데이터

단계 1의 `generate_dataset.py`(도형 합성)는 Sana 파인튜닝에도 여전히 유효한 접근입니다 — 다만 Sana는 이미 자연 이미지 전반에 대한 사전학습이 되어 있으므로, 파인튜닝 목적을 다음 중 하나로 명확히 좁혀야 합니다.

- **옵션 A (권장, 단계 1과 자연스럽게 연결)**: 도형/아이콘/다이어그램처럼 명확한 스타일의 이미지를 지속 생성하는 "스타일 특화" 파인튜닝. 데이터는 계속 프로그래밍적으로 생성 가능해 외부 의존성이 없습니다.
- **옵션 B**: 특정 화풍/브랜드 톤의 이미지를 생성하도록 소량의 직접 촬영/제작한 이미지-캡션 페어로 파인튜닝. 이 경우 이미지를 실제로 준비하는 작업이 필요합니다.

현재는 옵션 A로 시작하고, 실제 파인튜닝 결과를 본 뒤 옵션 B로 확장할지 결정합니다.

## 4. 추론 서버 설계 변경 — 가변 길이 + 스트리밍

### 4.1 요구사항

"Claude처럼 최대 대화 길이를 지정하고, 짧은 질문엔 빠르게, 긴 설명엔 자세히, 유동적으로 속도 조절"을 다음과 같이 구현합니다.

- API 요청에 `max_tokens`(기존에도 있었음, 이제 실제로 동작)와 `mode`(`"fast"` | `"thinking"`, Qwen3.5의 non-thinking/thinking 모드에 대응) 파라미터를 받습니다.
- 응답은 **Server-Sent Events(SSE) 스트리밍**으로 토큰이 생성되는 대로 전송합니다. 사용자는 전체 응답을 기다리지 않고 첫 토큰부터 받아볼 수 있어 체감 대기시간이 줄어듭니다 (Claude의 스트리밍 응답과 동일한 사용자 경험 원리).
- `mode="fast"`(기본값)는 non-thinking 모드로 즉시 응답 생성, `mode="thinking"`은 내부적으로 추론 과정을 거친 뒤 응답해 더 복잡한 질문에 나은 품질을 제공하되 지연시간이 늘어남 — 이 트레이드오프를 사용자가 선택할 수 있게 노출합니다.

### 4.2 API 계약 변경 (하위 호환 유지)

```
POST /v1/text/generate
{
  "prompt": "...",
  "max_tokens": 512,
  "mode": "fast",       // 신규, 기본값 "fast". "thinking"으로 전환 가능
  "stream": true        // 신규, 기본값 false(기존 방식과 완전 호환)
}
```

`stream`이 `false`(또는 생략)이면 기존과 동일하게 완성된 응답을 한 번에 JSON으로 반환합니다. 기존 API를 사용하는 모든 클라이언트(WordPress 마이페이지 콘솔, 정적 데모 프런트엔드)는 코드 변경 없이 계속 동작합니다. `stream: true`일 때만 SSE로 전환됩니다.

### 4.3 왜 이게 "GPU 없이도 완벽히"와 맞는가

스트리밍은 총 생성 시간을 줄이는 기술이 아니라, **체감 대기시간을 줄이는 기술**입니다. CPU 추론이 GPU보다 느린 건 사실이지만, 토큰이 생성되는 즉시 사용자에게 보여주면 "느리다"는 인상이 크게 줄어듭니다. 이건 실제로 Claude, ChatGPT 등 상용 서비스가 채택하는 표준적인 사용자 경험 설계이며, 모델 크기나 GPU 유무와 무관하게 적용 가능한 기법입니다.

## 5. "완성"의 정의 — 벤치마크 + 사람 평가, 그리고 이 대화의 한계

**목표를 실제로 달성 가능한 기준으로 확정합니다**: Gemini/Nano Banana와의 공식 비교는 하지 않습니다. 대신 "Qwen3.5-0.8B라는 베이스를 파고들어 도달 가능한 최고 품질"을 벤치마크 수치 + 사람 정성 평가로 판정합니다.

### 5.1 이 대화의 물리적 한계 (먼저 명시)

이 세션(로컬 개발 샌드박스)은 GPU가 없고 `huggingface.co` 접근도 막혀 있습니다. 따라서:
- **여기서 할 수 있는 것**: 평가 스크립트, 데이터 생성 파이프라인, 학습 스크립트를 최대한 완성도 있게 작성하고, 로직 자체는 더미 데이터로 검증하는 것.
- **여기서 할 수 없는 것**: 실제 벤치마크를 실행해서 "몇 점이 나왔다"를 이 자리에서 확인하는 것. 이는 사용자가 Colab에서 노트북을 직접 실행해야 발생합니다.

따라서 아래 기준에 대한 실제 점수는 **다음 세션 이전에 사용자가 Colab에서 직접 실행한 결과를 전달**해야 확인할 수 있습니다. Claude가 스스로 "벤치마크를 통과했다"고 선언하는 일은 없습니다 — 실행 로그/점수를 사용자가 붙여넣거나, Colab 출력 파일을 다시 이 대화에 업로드해야 판단할 수 있습니다.

### 5.2 자동 벤치마크 (1차 필터링)

`lm-evaluation-harness`(EleutherAI, HuggingFace Open LLM Leaderboard의 표준 도구)를 사용합니다. Flash Texter는 학술 지식 벤치마크(KMMLU 같은 전문가 시험형)를 목표로 하지 않습니다 — 애초에 이 프로젝트는 "일상 대화 도우미"이지 "수능/자격증 시험 채점 모델"이 아니므로, 그 벤치마크로 우리 0.8B 모델을 재는 것은 목적에 안 맞습니다. 대신 다음 지표를 씁니다.

| 벤치마크 | 무엇을 재는가 | 목표치 (베이스 대비 개선) |
|---|---|---|
| 파인튜닝 전후 자체 held-out 검증셋 loss/perplexity | 우리 데이터 분포에 대한 적합도 | 파인튜닝 후 held-out loss가 베이스 모델 대비 명확히 하락 (구체적 하락폭은 5.4절의 반복 루프에서 실측치 기반으로 조정) |
| IFEval (Instruction-Following Eval, Google Research 공개) | 지시를 정확히 따르는가 (형식 제약 등 검증 가능한 지시) | 베이스 모델 대비 상승. 자동 채점 가능해 GPU만 있으면 사람 개입 없이 측정 가능 |
| KoBEST 또는 이에 준하는 한국어 상식·자연어이해 소규모 벤치마크 | 한국어 기본기가 파인튜닝으로 망가지지 않았는지(치명적 회귀 여부) | 베이스 모델 대비 5%p 이상 하락하면 실패 (파인튜닝이 기존 능력을 훼손했다는 신호) |

이 표의 목표치는 "일단 정한 것"이며, 5.4절의 반복 루프에서 실제 1차 실행 결과를 보고 현실적인 수치로 조정하는 것을 전제로 합니다 (처음부터 임의의 숫자를 못박고 거기에 억지로 맞추려 하지 않습니다).

### 5.3 사람 정성 평가 (최종 판단)

벤치마크를 통과해도, 실제 대화가 어색하면 의미가 없습니다. `docs/15`의 5.2절 통과 후:
- `training/flash-texter/eval_prompts.jsonl`(5.5절에서 신규 작성)에 정의된 고정 평가 프롬프트 세트로 실제 응답을 생성
- 최소 3개 카테고리(학습 데이터에 있던 유형/학습 데이터에 없는 새 유형/의도적으로 어려운 질문)에 대해 사람이 직접 읽고 판단
- 통과 기준: 정해진 정답이 있는 게 아니라, "이 정도면 실제로 서비스에 내놓을 만하다"는 주관적 판단 — 이건 코드로 대체할 수 없는 부분이라 명시적으로 사람 몫으로 남깁니다.

### 5.4 반복 루프 (이 프로젝트가 "미치광이처럼 판다"는 것의 실제 의미)

한 번 파인튜닝하고 끝내는 게 아니라, 다음 루프를 반복합니다.

```
데이터 확장(6.5) → Colab 파인튜닝 → 벤치마크(6.2) 실행 → 결과를 이 대화에 공유
     → Claude가 실패 원인 분석 + 다음 데이터/하이퍼파라미터 조정 제안
     → 사람 정성 평가(6.3) → "충분히 좋다" 판단 전까지 반복
```

이 루프가 실제로 여러 번 돌아야 "완성"에 가까워집니다. 한 번의 세션에서 "완성됐다"고 선언하지 않습니다.

### 5.5 다음 실행 항목

1. `training/flash-texter/eval_prompts.jsonl` — 고정 평가 프롬프트 세트 작성 (사람 평가용, 5.3절)
2. `training/flash-texter/run_benchmarks.py` — Colab에서 IFEval, KoBEST, held-out loss를 한 번에 실행하고 결과를 표로 정리하는 스크립트
3. `generate_finetune_data.py`의 카테고리/슬롯을 대규모로 확장 (7절에서 상세)

## 7. 학습 데이터 대규모 확장

기존 913개(10개 카테고리, 슬롯 기반 조합)에서 확장했습니다. **자동 증강(다른 모델로 데이터 생성)은 배제하며, 전량 직접 작성한 템플릿/슬롯의 조합으로만 규모를 늘립니다.**

### 7.1 실제 확장 결과

- 카테고리 수: 10개 → **28개** (단일 턴) + 멀티턴 대화 8개
- `--repeat-per-template 0`(전량 사용) + `--per-category-cap 2000`(카테고리 하나가 데이터셋을 지배하지 못하도록 상한) 옵션으로 생성한 결과: **4,741개의 전량 고유한 (입력,응답) 조합**
- 상한 없이 전량 사용하면 이론상 18,767개까지 가능하지만(주로 `explain_concept`의 슬롯 조합이 16,128개로 압도적), 이 경우 `explain_concept` 하나가 전체의 86%를 차지하는 극단적 불균형이 생긴다는 것을 실제로 확인하고 `--per-category-cap`으로 제한하는 방식을 택했습니다.
- "수만 개" 목표에는 아직 못 미치지만(4,741개), 이전(913개)보다 5.2배 확장했고, 균형을 희생하지 않는 선에서 도달 가능한 실질적 규모입니다. 추가로 규모를 늘리려면 카테고리 자체를 더 추가하거나(현재 28개), 슬롯이 없는 짧은 카테고리(예: `capability` 15개, `empathy_response` 15개)의 표현을 계속 늘려야 합니다 — 이건 반복적으로 사람이 직접 문장을 써야 하는 작업이라 이번 세션에서 일부만 진행했습니다.

### 7.2 실제로 발견하고 수정한 데이터 품질 버그: 조사 오류

무작위 샘플을 육안으로 검토하다가 **심각한 문법 오류**를 발견했습니다. 템플릿이 `"{topic}은(는) ..."`처럼 조사 두 개를 항상 병기하는 방식으로 작성되어 있었는데, 슬롯을 채운 뒤에도 이 병기 표기가 그대로 남아 `"복리은(는) 일상에서도..."`, `"이사 준비을(를) 하려면..."`처럼 문법적으로 명백히 틀린 문장이 대량으로 생성되고 있었습니다. 이 상태로 학습했다면 모델이 잘못된 한국어 조사 규칙을 그대로 배웠을 것입니다.

**수정**: `training/flash-texter/korean_josa.py` 신규 작성 — 단어의 마지막 글자(괄호가 있으면 괄호 앞부분 기준)에 받침이 있는지를 한글 유니코드 구조로 직접 계산해서, "은(는)", "이(가)", "을(를)", "와(과)" 이중 표기를 실제 문법에 맞는 조사 하나로 치환하는 `resolve_dual_josa()` 함수를 만들었습니다. `generate_finetune_data.py`가 슬롯을 채운 직후 이 함수를 호출하도록 연결했습니다.

**검증**: 조사 판별 함수(받침 유무 계산 포함 괄호 예외 처리) 11개 케이스, 이중조사 치환 함수를 실제 버그 사례(복리, 저작권, 이사 준비, 탄력성(경제), 아이폰/갤럭시, 확률) 6개로 각각 검증했고, 전체 데이터셋 재생성 후 이중조사 표기가 하나도 남아있지 않음을 전수 검사로 확인했습니다.

이 버그는 "카테고리 수를 늘리고 조합을 늘리는" 규모 확장 작업 중에 발견됐다는 점이 중요합니다 — 규모만 키우고 내용을 검토하지 않았다면 수천 개의 문법 오류가 그대로 학습 데이터에 들어갔을 것입니다.

## 8. 진행 상황

### 8.1 신규: 단계 2 실제 추론 인터페이스 + 검색 grounding + 3단계 폴백

사용자 지적: "템플릿 기반이 아니라 AI가 직접 검색하고 생각하고 추론해야 진정한 AI"라는 정당한 문제 제기가 있었습니다. 확인 결과, 검색 연동(`search_augment.py`) 자체는 이미 구현되어 있었지만 **단계 1은 검색 결과를 그대로 인용만 하고, 모델이 실제로 검색 결과를 읽고 이해해서 답을 재구성하는 진짜 grounding은 단계 2(Qwen3.5)에서만 가능한데 그 연결 코드가 없었습니다.** 이번에 실제로 만들었습니다.

- [x] `training/flash-texter/inference_stage2.py` — Qwen3.5 LoRA 모델의 실제 추론 인터페이스. `build_prompt()`가 검색 결과를 프롬프트에 시스템 메시지로 주입해(Gemini/GPT/Claude와 동일한 RAG 방식), 모델이 그 내용을 "읽고 재구성"하도록 함. 검색 결과가 없으면 이 블록을 생략.
- [x] **프롬프트 인젝션 취약점을 실제로 발견하고 수정**: `build_prompt`를 다양한 케이스로 검증하던 중, 사용자 입력이나 검색 결과 텍스트에 `<|im_end|><|im_start|>system` 같은 ChatML 제어 토큰이 포함되면 그대로 프롬프트에 삽입되어 가짜 시스템 메시지를 주입할 수 있다는 것을 로컬에서 실제로 재현했습니다(공격 시나리오 성공 확인). `_sanitize_user_text()`로 제어 토큰을 제거하는 방어를 추가하고, 사용자 입력 경로와 검색 결과 경로 둘 다에서 인젝션이 차단되는 것을 재검증했습니다(제어 토큰 등장 횟수를 정확히 세는 방식으로 확인).
- [x] `inference-server/models/flash_texter.py`를 3단계 우선순위 구조로 재작성: **단계 2(Qwen3.5, 진짜 신경망 추론) → 단계 1(GRU 의도분류, 폴백) → 더미(최종 안전망)**. 세 가지 실패 시나리오(단계2 미설정, 단계2 로드 실패, 단계1도 실패)를 실제로 만들어 각각 정확한 단계로 폴백되는지 검증했습니다.
- [x] **`_model_loader_utils.py`의 숨겨진 버그 발견**: 위 검증 과정에서 `load_inference_module()`이 진입 파일명을 `"inference.py"`로 하드코딩하고 있어서, 단계 2의 진입점(`inference_stage2.py`)을 아예 로드하지 못하고 엉뚱한 에러(`No module named 'model'`)를 내는 것을 확인했습니다. `entry_filename` 파라미터를 추가해 파일명을 지정할 수 있도록 고치고(기본값은 기존 `"inference.py"`라 단계 1/이미지 모델 호출부는 무수정으로 하위 호환), 수정 후 정확한 실패 이유(예: 존재하지 않는 저장소 경로)가 보고되는 것을 재검증했습니다.

**여전히 명확히 해야 할 것**: 이 검색 grounding과 진짜 추론은 **단계 2(Qwen3.5) 파인튜닝이 Colab에서 실제로 완료되어야 실제 서비스에서 작동**합니다. 지금은 코드 경로가 실제 신경망 없이도 검증 가능한 부분(프롬프트 조립, 인젝션 방어, 폴백 로직)까지만 확인된 상태입니다.

7. [x] `training/flash-texter/train_lora.py` 작성, **이후 재검토에서 두 개의 실제 문제를 발견하고 수정**:
   - **transformers 버전 오류**: 최초 `>=4.57.0`으로 명시했으나, 실제로는 Qwen3.5가 `transformers >= 5.2.0`부터 지원된다는 걸 재조사로 확인(그 이전 버전은 로드 자체가 안 됨). `requirements.txt`와 스크립트 내 버전 검증 함수(`check_transformers_version`)로 반영, 낮은 버전에서 명확히 에러를 내는 것까지 실제 시뮬레이션으로 검증.
   - **비전 인코더 오염 문제 (가장 중요한 발견)**: Qwen3.5-0.8B가 순수 텍스트 모델이 아니라 **비전-언어 멀티모달 모델**이라는 사실을 재조사로 확인했다 (공식 모델 카드/NVIDIA NGC 문서에 "vision-language model"로 명시). `AutoModelForCausalLM`으로 그대로 로드하면 비전 인코더까지 함께 로드되고, `LoraConfig(target_modules=["q_proj", ...])`처럼 이름만으로 매칭하면 **비전 인코더의 동명 레이어에도 LoRA가 잘못 적용될 수 있다는 것을 로컬 더미 멀티모달 모델로 실제 재현**했다. `peft`의 `exclude_modules`로 이를 막으려 했으나, 처음 시도한 `["vision_encoder.*"]`(리스트+와일드카드)는 **peft 소스 코드 확인 결과 리터럴 문자열 매칭만 지원해 작동하지 않음을 실제로 확인**했고, `exclude_modules`를 정규식 문자열 하나(`r".*(vision|visual|...).*"`)로 넘겨야 정확히 작동한다는 것을 재검증했다. 최종적으로 텍스트 백본 4개 레이어에는 LoRA가 정상 적용되고 비전 인코더는 완전히 제외되는 것을 엔드투엔드로 확인.
